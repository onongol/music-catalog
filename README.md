# Каталог музыкальных альбомов

Веб-приложение на Django для каталогизации музыки: исполнители, альбомы и
треклисты. Веб-интерфейс, REST API и админка над одной моделью данных.

Все документы лежат в каталоге [`specs/`](specs/) и являются частью результата.

---

## Ключевая особенность модели

Требование задания — *одна и та же песня может входить в разные альбомы
с разными порядковыми номерами*. Поэтому **номер трека хранится не в песне,
а в связи между песней и альбомом**:

```
Artist ──1:N──▶ Album ──1:N──▶ AlbumTrack ◀──N:1── Song
                                    │
                                track_number
```

`AlbumTrack` — отдельная запись, которая связывает песню с альбомом и хранит
её номер в треклисте. Благодаря этому одна и та же песня может:

| Песня | Альбом | Номер |
|-------|--------|-------|
| Bohemian Rhapsody | A Night at the Opera (1975) | **11** |
| Bohemian Rhapsody | Greatest Hits (1981) | **1** |

Песня при этом хранится в базе **в одном экземпляре**. Демо-данные содержат этот
пример: он виден на странице `/songs/` сразу после запуска.

Ограничения проверяются самой базой данных, а не только формами:

* номер трека уникален внутри альбома — `UniqueConstraint(album, track_number)`;
* песня не может входить в один альбом дважды — `UniqueConstraint(album, song)`;
* название альбома уникально у исполнителя — `UniqueConstraint(artist, title)`;
* год выпуска — от 1860 до 2100 (`CheckConstraint`); формы и API дополнительно
  сужают верхнюю границу до следующего года;
* удаление исполнителя удаляет его альбомы, но **не трогает песни**.

Подробности — в [`specs/001-music-catalog/data-model.md`](specs/001-music-catalog/data-model.md).

## Стек

Python 3.13 · Django 5.2 · Django REST Framework · PostgreSQL 17 (в Docker) /
SQLite (локально) · Gunicorn · WhiteNoise · pytest + factory_boy
Фронтенд: Vite 8 · Tailwind CSS 4 · django-vite

Интерфейс — серверный рендеринг Django, стили собираются Vite с плагином
`@tailwindcss/vite`. Django берёт готовые ассеты через `django-vite`: в обычном
режиме по `manifest.json`, а с `DJANGO_VITE_DEV_MODE=True` — напрямую с
дев-сервера Vite, с горячей перезагрузкой. В Docker сборка выполняется на отдельной стадии с Node. В рабочий образ не попадают Node.js, npm, Vite и node_modules; туда копируются только исходники приложения и готовые статические файлы.

**Почему без frontend frameworks.** Объём задания — каталог с веб-интерфейсом, поэтому серверного рендеринга Django достаточно. При этом REST API спроектирован самостоятельно (`/api/` с фильтрами и вложенными данными), поэтому Vue, React или другое SPA подключается к нему без единого изменения на бэкенде.

## Запуск через Docker

Требуется только Docker с плагином Compose.

```bash
git clone https://github.com/onongol/music-catalog.git
cd music-catalog
docker compose up
```

Приложение поднимется на **http://localhost:8000/**. Никаких дополнительных
шагов не нужно: контейнер сам применит миграции, соберёт статику, загрузит
демо-данные и создаст администратора. Команду можно запускать повторно: уже выполненные шаги не создадут дубликаты и не повредят существующие данные.

Учётная запись админки: **admin@example.com / admin** (демонстрационная, задаётся
в `docker-compose.yml`).

```bash
docker compose logs -f web    # логи
docker compose down           # остановить
docker compose down -v        # остановить и удалить данные PostgreSQL
```

## Локальный запуск

Требуется Python 3.13 (проект работает и на 3.11+). База — SQLite, внешние
сервисы не нужны.

```bash
git clone https://github.com/onongol/music-catalog.git
cd music-catalog

python3 -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements-dev.txt

npm install && npm run build       # собрать стили (нужен Node >= 20)

python manage.py migrate
python manage.py seed_demo         # демо-данные, необязательно
python manage.py runserver
```

Готово: **http://127.0.0.1:8000/**

Доступ в админку локально (вход по email, поле «имя пользователя» отсутствует):

```bash
python manage.py createsuperuser
```

Собранные файлы стилей и скриптов не хранятся в репозитории — каталог `static/` в `.gitignore`,
поэтому шаг `npm run build` обязателен при локальном запуске. В Docker он
выполняется автоматически.

При работе над стилями удобнее горячая перезагрузка — в отдельном терминале:

```bash
npm run dev                                    # дев-сервер Vite на :5173
DJANGO_VITE_DEV_MODE=True python manage.py runserver
```

Файл `.env` не обязателен — рабочие значения по умолчанию заданы в
`config/settings.py`. Если нужно переопределить настройки, скопируйте
[`.env.example`](.env.example) в `.env`. Для работы с PostgreSQL достаточно
задать `DATABASE_URL`.

Частые команды собраны в `Makefile`: `make run`, `make test`, `make seed`,
`make docker`, `make help`.

## Что умеет приложение

| Раздел | Адрес | Возможности |
|--------|-------|-------------|
| Главная | `/` | сводка каталога, недавние альбомы, песни из нескольких альбомов |
| Исполнители | `/artists/` | список с числом альбомов, поиск, CRUD |
| Альбомы | `/albums/` | список с исполнителем, годом и числом треков; поиск, фильтр по исполнителю и году; CRUD |
| Карточка альбома | `/albums/<id>/` | треклист по порядку, добавление песни, смена номера, удаление трека |
| Песни | `/songs/` | список с числом альбомов, поиск, CRUD |
| Карточка песни | `/songs/<id>/` | все альбомы, где есть песня, с её номером в каждом |
| API | `/api/` | REST с просмотром в браузере |
| Админка | `/admin/` | треклист редактируется inline в карточке альбома |

При попытке занять уже используемый номер или добавить песню в альбом повторно
интерфейс показывает понятное сообщение об ошибке, а данные остаются нетронутыми.

## REST API

| Метод | Путь | Действие |
|-------|------|----------|
| `GET` `POST` | `/api/artists/` | исполнители |
| `GET` `PUT` `PATCH` `DELETE` | `/api/artists/{id}/` | |
| `GET` `POST` | `/api/albums/` | альбомы (ответ включает вложенный треклист) |
| `GET` `PUT` `PATCH` `DELETE` | `/api/albums/{id}/` | |
| `GET` `POST` | `/api/songs/` | песни (ответ включает все альбомы с номерами) |
| `GET` `PUT` `PATCH` `DELETE` | `/api/songs/{id}/` | |
| `GET` `POST` | `/api/tracks/` | вхождения песен в альбомы |
| `GET` `PUT` `PATCH` `DELETE` | `/api/tracks/{id}/` | |

Фильтры: `?search=`, `?artist=`, `?release_year=`, `?album=`, `?ordering=`.

Ключевой случай в ответе API:

```bash
curl 'http://localhost:8000/api/songs/?search=Bohemian'
```

```json
{
  "id": 4,
  "title": "Bohemian Rhapsody",
  "album_count": 2,
  "appears_on": [
    { "album_title": "A Night at the Opera", "release_year": 1975, "track_number": 11 },
    { "album_title": "Greatest Hits",        "release_year": 1981, "track_number": 1  }
  ]
}
```

Если запрос нарушает одно из правил данных, API возвращает ошибку `400` с понятным описанием проблемы:

```bash
curl -X POST http://localhost:8000/api/tracks/ \
     -H 'Content-Type: application/json' \
     -d '{"album": 1, "song": 2, "track_number": 11}'
```

```json
{ "non_field_errors": ["Номер 11 уже занят в этом альбоме."] }
```

Полный контракт — [`specs/001-music-catalog/contracts/api.md`](specs/001-music-catalog/contracts/api.md).

## Принятые допущения

Полный список — в `plan.md`, раздел «Принятые допущения». Кратко:

* **Песня не привязана к исполнителю** — в задании у неё только название.
  Исполнитель определяется через альбом, что естественно поддерживает сборники
  и каверы.
* **Аутентификация не реализована** — CRUD открыт всем. Для боевого применения
  понадобились бы права доступа; в рамках тестового задания это сознательное
  упрощение. При этом модель пользователя подменена заранее (см. ниже).
* **Собственная модель пользователя с входом по email** заведена сразу, хотя
  аутентификация вне объёма. Django рекомендует делать это до первой миграции:
  позже замена `AUTH_USER_MODEL` требует ручного переноса всех внешних ключей.
  Реализована только модель — не функциональность.
* **Номера треков не перенумеровываются автоматически** при удалении трека:
  неявная перезапись пользовательских данных опаснее пропуска в нумерации.
