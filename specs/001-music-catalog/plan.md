
Каталог — одно приложение вместо трёх: предметная область неделима, разнесение
`artists/albums/songs` по отдельным приложениям породило бы циклические импорты
без единой выгоды. Модель пользователя вынесена в `users` отдельно — она не
относится к предметной области каталога.

Внутри `catalog/views/` разделение обратное: модули `artists`, `albums`, `songs`,
`tracks` не ссылаются друг на друга, поэтому дробление ничего не стоит и даёт
навигацию по разделам.

## 3. Ключевое архитектурное решение

Требование «одна песня — разные альбомы с разными номерами» реализуется
**связью многие-ко-многим через явную модель** `AlbumTrack`:

```
Artist ──1:N──▶ Album ──1:N──▶ AlbumTrack ◀──N:1── Song
                                    │
                                 track_number
```

`AlbumTrack` — не техническая таблица связи, а полноценная сущность предметной
области: у неё есть собственный атрибут `track_number`, собственные ограничения
целостности и собственные URL-ы для CRUD.

**Отвергнутые альтернативы:**

* `Song.album = ForeignKey(Album)` + `Song.track_number` — прямо противоречит
  требованию: песню пришлось бы дублировать для каждого альбома;
* `ManyToManyField` без `through` — негде хранить `track_number`;
* `Album.track_numbers = JSONField` — теряются ограничения БД (принцип III
  конституции) и возможность фильтровать/сортировать средствами СУБД.

## 4. Инварианты на уровне БД

Согласно принципу III конституции:

| Ограничение | Требование |
|-------------|------------|
| `UniqueConstraint(artist, title)` на `Album` | FR-07 |
| `CheckConstraint(1860 ≤ release_year ≤ 2100)` на `Album` | FR-08 |
| `UniqueConstraint(album, track_number)` на `AlbumTrack` | FR-15 |
| `UniqueConstraint(album, song)` на `AlbumTrack` | FR-16 |
| `PositiveSmallIntegerField` + `MinValueValidator(1)` | FR-17 |
| `unique=True` на `Artist.name` | FR-03 |

Верхняя граница года в `CheckConstraint` — константа 2100, а не `now().year + 1`:
`CheckConstraint` компилируется в DDL при миграции и не может зависеть от
времени выполнения. Точная граница «текущий год + 1» (FR-08) проверяется
валидатором модели и формы.

Нарушения ограничений перехватываются на уровне форм и сериализаторов и
превращаются в человекочитаемые сообщения (FR-25).

## 5. Производительность

Для NFR-01 во всех списковых представлениях:

* `Artist`: `annotate(album_count=Count("albums"))`;
* `Album`: `select_related("artist")` + `annotate(track_count=Count("tracks"))`;
* `Song`: `annotate(album_count=Count("album_entries"))`;
* карточка альбома: `prefetch_related("tracks__song")`;
* карточка песни: `select_related("album__artist")` на вхождениях.

## 6. Интерфейс

Server-side rendering на Django CBV. Стили — Tailwind CSS 4, собираются Vite
из `assets/css/input.css` в `static/dist/`. Ноль внешних CDN, ноль JavaScript
в рантайме (NFR-04).

Связку с Django обеспечивает `django-vite`. Ссылка на стили в шаблоне
разрешается двумя способами в зависимости от `dev_mode`:

| Режим | Что подставляется | Когда |
|-------|-------------------|-------|
| `dev_mode = False` (по умолчанию) | путь из `manifest.json` готовой сборки | обычный запуск, Docker |
| `dev_mode = True` | адрес дев-сервера Vite + клиент HMR | `DJANGO_VITE_DEV_MODE=True` рядом с `npm run dev` |

Собранные ассеты **не хранятся в репозитории** (`static/` в `.gitignore`):
артефакт сборки в git создаёт два источника истины и шумит в diff. Цена —
обязательный `npm run build` при локальном запуске; в Docker сборку выполняет
отдельная стадия на `node:24-slim`, её результат копируется в питоновский образ.

Два решения, отличающиеся от типового шаблона django-vite:

* **`source(none)` в `input.css`.** Без него Tailwind сканирует весь корень
  проекта и вылавливает «классы» из `.py` и `.md`. В Docker-контекст попадают
  только шаблоны, поэтому вывод расходился бы с локальным. С явным `@source`
  сборка воспроизводима — хеши файлов совпадают локально и в образе.
* **Вывод в `static/dist/`, а не в `static/`.** Позволяет включить
  `emptyOutDir: true`: имена файлов содержат хеш, и без очистки каталога
  бандлы прошлых сборок копились бы бесконечно.

**Почему не Vue.** Стек команды включает Vue 3, Vite, Pinia и Quasar, но объём
задания — каталог с веб-интерфейсом, и SPA его не улучшает. При этом REST API
спроектирован как самостоятельный слой, так что фронтенд на Vue подключается
к нему без изменений на бэкенде.

| URL | Назначение |
|-----|------------|
| `/` | сводка каталога (FR-22) |
| `/artists/`, `/artists/<pk>/`, `+ create/edit/delete` | FR-01…FR-04 |
| `/albums/`, `/albums/<pk>/`, `+ create/edit/delete` | FR-05…FR-10 |
| `/albums/<pk>/tracks/add/`, `/tracks/<pk>/edit/`, `/tracks/<pk>/delete/` | FR-13…FR-15 |
| `/songs/`, `/songs/<pk>/`, `+ create/edit/delete` | FR-11…FR-19 |
| `/api/` | DRF browsable API (FR-23…FR-26) |
| `/admin/` | админка Django |

## 8. Docker

Два сервиса в `docker-compose.yml`:

* `db` — PostgreSQL 17 с `healthcheck`;
* `web` — приложение, стартует после `db: service_healthy`.

`entrypoint.sh` при старте выполняет `migrate`, `collectstatic` и `seed_demo`,
после чего запускает Gunicorn. Это закрывает FR-29: «без ручных шагов».
`.env` не требуется — рабочие значения по умолчанию заданы в `docker-compose.yml`.

## 9. Принятые допущения

1. **Песня не привязана к исполнителю.** В спецификации у песни только название.
   Исполнитель определяется через альбом, что естественно поддерживает сборники
   и каверы.
2. **Длительность песни не хранится.** Её нет в требованиях.
3. **Аутентификация отсутствует, но модель пользователя своя.** Публичный CRUD —
   сознательное упрощение тестового задания; для production потребовались бы
   права доступа. При этом `AUTH_USER_MODEL` подменён на `users.User` сразу
   (NFR-05) — см. раздел 10.
4. **Номера треков не перенумеровываются автоматически** при удалении трека.
   Это не заявлено в требованиях, а неявная перезапись данных опаснее дырки
   в нумерации.
5. **`DEBUG=True` по умолчанию** для локального запуска; в контейнере
   переключается переменной окружения.

## 10. Модель пользователя (NFR-05)

Приложение `users` содержит `User(AbstractUser)`, где `username` удалён,
а `USERNAME_FIELD = "email"`. `AUTH_USER_MODEL = "users.User"` задан до первой
миграции.

**Почему это сделано, хотя аутентификация не входит в объём.** Документация
Django прямо рекомендует подменять модель пользователя в начале проекта, даже
если стандартная устраивает. Причина в стоимости отката: после того как
`auth_user` создана и на неё сослались внешние ключи, переход требует ручной
миграции с переносом данных и правкой всех зависимостей. Пока проект не
развёрнут, цена нулевая — достаточно пересоздать базу.

**Что потребовалось переопределить:**

| Компонент | Причина |
|-----------|---------|
| `UserManager` | штатный `BaseUserManager.create_user` принимает `username` |
| `UserAdminCreationForm`, `UserAdminChangeForm` | штатные формы указывают `username` в `fields` и `field_classes` |
| `UserAdmin` (`fieldsets`, `ordering`, `search_fields`) | всюду, где Django ожидает `username`, стоит `email` |

**Влияние на запуск.** `createsuperuser --noinput` читает `DJANGO_SUPERUSER_EMAIL`
вместо `DJANGO_SUPERUSER_USERNAME`, поэтому переменные в `docker-compose.yml`
и условие в `entrypoint.sh` заданы по email.

**Границы решения.** Регистрация, вход для обычных пользователей и разграничение
прав по-прежнему вне объёма. Реализована только модель — точка расширения,
а не функциональность.
