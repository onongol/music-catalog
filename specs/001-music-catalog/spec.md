# Спецификация: Каталог музыкальных альбомов

* **ID функции:** 001-music-catalog
* **Статус:** принята
* **Дата:** 2026-08-19

---

## 1. Цель

Веб-приложение для ведения каталога музыки: исполнители, их альбомы и состав
треков в альбомах. Пользователь должен видеть каталог, искать по нему и
редактировать содержимое через веб-интерфейс.

## 2. Границы

**Входит в объём:**

* CRUD по исполнителям, альбомам, песням;
* управление треклистом альбома (состав песен и их порядок);
* просмотр, поиск, фильтрация каталога;
* REST API, отражающий те же операции;
* демонстрационные данные для быстрой проверки.

**Не входит в объём:**

* аутентификация и роли пользователей (кроме стандартной админки Django) —
  функциональность не реализуется, но модель пользователя подменяется заранее,
  см. NFR-05;
* загрузка аудиофайлов и обложек;
* импорт из внешних сервисов (Spotify, MusicBrainz, Discogs);
* многоязычный интерфейс, рейтинги, плейлисты, комментарии.

## 3. Сущности предметной области

| Сущность       | Атрибуты                                     | Примечание |
|----------------|----------------------------------------------|------------|
| **Исполнитель**| Имя                                          | Имя уникально |
| **Альбом**     | Название, Исполнитель, Год выпуска           | Принадлежит ровно одному исполнителю |
| **Песня**      | Название                                     | Существует независимо от альбомов |
| **Трек**       | Альбом, Песня, Порядковый номер              | Связь «песня в альбоме» |

### 3.1. Ключевое требование

Порядковый номер — свойство **вхождения песни в альбом**, а не самой песни.
Одна песня может входить в несколько альбомов (студийный альбом, сборник,
концертник) и иметь в каждом из них свой номер.

Пример, который обязан корректно храниться:

```
Песня «Bohemian Rhapsody»
  ├─ альбом «A Night at the Opera» (1975) — трек №11
  └─ альбом «Greatest Hits»        (1981) — трек №1
```

## 4. Функциональные требования

### Исполнители

| ID | Требование |
|----|------------|
| FR-01 | Пользователь видит список исполнителей с количеством альбомов у каждого |
| FR-02 | Пользователь создаёт, редактирует и удаляет исполнителя |
| FR-03 | Имя исполнителя уникально; попытка создать дубликат отклоняется с понятным сообщением |
| FR-04 | На карточке исполнителя показаны все его альбомы, отсортированные по году выпуска |

### Альбомы

| ID | Требование |
|----|------------|
| FR-05 | Пользователь видит список альбомов с исполнителем, годом и числом треков |
| FR-06 | Пользователь создаёт, редактирует и удаляет альбом, выбирая исполнителя из списка |
| FR-07 | Пара «исполнитель + название альбома» уникальна |
| FR-08 | Год выпуска ограничен диапазоном от 1860 до «текущий год + 1» |
| FR-09 | На карточке альбома показан треклист, отсортированный по порядковому номеру |
| FR-10 | Удаление исполнителя удаляет его альбомы; песни при этом сохраняются |

### Песни и треклисты

| ID | Требование |
|----|------------|
| FR-11 | Пользователь видит список песен и число альбомов, в которые входит каждая |
| FR-12 | Пользователь создаёт, редактирует и удаляет песню |
| FR-13 | Пользователь добавляет существующую песню в альбом, указывая порядковый номер |
| FR-14 | Пользователь меняет порядковый номер трека и удаляет трек из альбома |
| FR-15 | Порядковый номер уникален в пределах альбома: два трека не могут иметь номер 3 |
| FR-16 | Одна песня не может быть добавлена в один и тот же альбом дважды |
| FR-17 | Порядковый номер — целое число ≥ 1 |
| FR-18 | На карточке песни перечислены все альбомы с номером песни в каждом из них |
| FR-19 | Удаление песни убирает её из треклистов, но не затрагивает сами альбомы |

### Поиск и навигация

| ID | Требование |
|----|------------|
| FR-20 | Поиск по имени исполнителя, названию альбома и названию песни |
| FR-21 | Фильтрация альбомов по исполнителю и по году выпуска |
| FR-22 | Главная страница показывает сводку каталога и ссылки на разделы |

### API

| ID | Требование |
|----|------------|
| FR-23 | REST API предоставляет CRUD по исполнителям, альбомам, песням и трекам |
| FR-24 | Ответ по альбому включает вложенный треклист с номерами и названиями песен |
| FR-25 | Нарушение инвариантов FR-15/FR-16 возвращает HTTP 400 с описанием ошибки |
| FR-26 | API самодокументирован: доступна просматриваемая в браузере схема |

### Эксплуатация

| ID | Требование |
|----|------------|
| FR-27 | Команда наполняет базу демонстрационными данными, включая песню в двух альбомах |
| FR-28 | Проект запускается локально по инструкции из README |
| FR-29 | Проект запускается командой `docker compose up` без ручных шагов |

## 5. Сценарии приёмки

**Сценарий 1 — песня в двух альбомах (ключевой)**

1. Создан исполнитель «Queen».
2. Созданы альбомы «A Night at the Opera» (1975) и «Greatest Hits» (1981).
3. Создана песня «Bohemian Rhapsody».
4. Песня добавлена в первый альбом с номером 11, во второй — с номером 1.
5. Треклист первого альбома показывает её под №11, второго — под №1.
6. Карточка песни показывает оба альбома с разными номерами.

**Сценарий 2 — конфликт номеров**

1. В альбоме уже есть трек с номером 3.
2. Пользователь пытается добавить другую песню с номером 3.
3. Система отклоняет операцию с сообщением о занятом номере; данные не изменены.

**Сценарий 3 — повторное добавление песни**

1. Песня уже входит в альбом.
2. Пользователь пытается добавить её в тот же альбом ещё раз.
3. Система отклоняет операцию; треклист не изменился.

**Сценарий 4 — удаление исполнителя**

1. У исполнителя два альбома, в треклистах — пять разных песен.
2. Исполнитель удалён.
3. Альбомы удалены, все пять песен остались в каталоге.

**Сценарий 5 — холодный старт**

1. На чистой машине выполнено `docker compose up`.
2. Приложение отвечает на `http://localhost:8000/`, миграции применены,
   демо-данные загружены, сценарий 1 воспроизводим через интерфейс.

## 6. Нефункциональные требования

| ID | Требование |
|----|------------|
| NFR-01 | Списки не должны страдать от N+1 запросов: связанные объекты подгружаются заранее |
| NFR-02 | Все функциональные требования покрыты автотестами |
| NFR-03 | Секреты и настройки читаются из переменных окружения, а не из кода |
| NFR-04 | Интерфейс не обращается к внешним CDN. Стили собираются заранее: для запуска проекта Node не требуется, он нужен только при правке стилей |
| NFR-05 | Проект использует собственную модель пользователя с email вместо имени пользователя. Сама аутентификация в объём не входит, но модель задаётся до первой миграции — позже её замена обходится несоизмеримо дороже |
