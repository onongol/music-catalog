# Конституция проекта Music Catalog

Набор неизменяемых принципов, которым подчиняются спецификация, план и реализация.
Любое решение, противоречащее конституции, требует явной правки этого документа.

## I. Spec-Driven Development

Порядок работы строго фиксирован:

```
spec.md  →  plan.md  →  tasks.md  →  код  →  тесты
 (что)      (как)       (шаги)
```

* `spec.md` описывает **что** и **зачем**, без единого упоминания технологий.
* `plan.md` описывает **как**: стек, архитектура, схема данных, контракты.
* `tasks.md` — атомарные, проверяемые задачи, каждая ссылается на требование из `spec.md`.
* Код не пишется раньше, чем требование зафиксировано в спецификации.

## II. Модель данных первична

Ключевое требование предметной области — **одна и та же песня входит в разные альбомы
с разными порядковыми номерами**. Схема данных обязана выражать это структурно,
а не соглашением или дублированием строк. Никаких «песня принадлежит альбому».

## III. Целостность обеспечивается базой, а не приложением

Каждое инвариантное правило (уникальность номера трека, отсутствие дублей,
допустимый диапазон года) закрепляется ограничением на уровне СУБД
(`UniqueConstraint`, `CheckConstraint`), а не только валидацией формы.
Форма может продублировать проверку ради UX, но источник истины — база.

## IV. Тестируемость

Каждое функциональное требование покрыто автотестом. Тесты не обращаются к сети,
не зависят от порядка выполнения и не требуют предварительно наполненной БД.

## V. Запуск в одну команду

Проект поднимается либо `docker compose up`, либо тремя командами локально.
Никаких недокументированных шагов, ручных правок конфигов и «сначала создайте БД».

## VI. Разумная простота

Тестовое задание — не повод для микросервисов, Celery и Redis. Выбирается самый
простой инструмент, решающий задачу. Каждая зависимость в `requirements.txt`
должна быть оправдана требованием из `spec.md`.
